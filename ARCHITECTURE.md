# Предлагаемая архитектура
Архитектура описывает целевую систему, а не готовую игру. Техническая база S01 проверена прототипом и приемкой на iQOO15R / Android16: версии и ограничения см. tools/s01/versions.json и docs/adr/0001-s01-stack.md. S02 создает структуру каталогов; это не реализация будущих компонентов.

## Компоненты
| Компонент | Предложение | Ответственность |
|---|---|---|
| Game Android | Godot 4, GDScript, небольшой Kotlin-плагин обновления APK | 2D, UI из JSON, визуализация боев, локальные ресурсы |
| Game Studio | React + TypeScript; Android Kotlin WebView | визуальные редакторы, ZIP, версии, управление |
| API и workers | TypeScript на Node.js, Fastify | авторизация, экономика, бой, чат, жители |
| База | PostgreSQL | транзакции, журнал наград, аккаунты, память, версии |
| Очереди | сначала задания в PostgreSQL с lease; Redis при подтвержденной необходимости | фоновые задачи без лишних сервисов |
| Ресурсы | неизменяемые файлы по hash на VPS за HTTPS | манифест, скачивание, версии |
| Развертывание | отдельные Compose-проекты для test/prod после обследования | изоляция, лимиты и откат |
| Сборка | CI/среда Codex, не обязательная тяжелая сборка на игровом VPS | оба APK и проверка артефактов |

Godot PCK поддерживает пакеты, но пользовательский ZIP не передается напрямую в load_resource_pack: пакет может содержать код. Принимаем только разрешенные JSON/изображения/атласы/аудио и при необходимости собираем доверенный пакет в pipeline. Не дублируем боевую логику в GDScript и TypeScript: сервер - единственный расчет, клиент - проигрыватель событий и интерактивных команд.

## Бой и сеть
Снимок команд, content_version, seed RNG, battle_id и simulation_version закрепляются до боя. Сервер проверяет принадлежность героев, экипировку и права на скорость/skip.
Фиксированный шаг и целочисленные расчеты по документированным формулам; порядок одновременных событий детерминирован.
В обычном бою сервер пошагово выполняет бой, отправляет события по WebSocket и принимает команды основной способности с battle_id/sequence. Команды относятся к серверному текущему состоянию, просроченные/повторные отклоняются или дают сохраненный ответ. Нельзя заранее рассчитать весь бой и затем притворяться, что ручные команды влияют на него.
Скорость ×N меняет отношение серверного игрового времени к реальному, не урон и не последовательность RNG. 90 секунд - игровое время.
Skip - отдельный быстрый прогон той же функции шага с авто-способностями, только при разрешении режима, прохождения и VIP. Результаты совпадают с тем же seed/снимком/автокомандами при обычном исполнении.
Повторное соединение получает snapshot и непрочитанные события. Политика при потере связи: предложено автоматическое применение способностей до окончания; зафиксировать на S18. Награда и результат ровно один раз.

## Данные и транзакции
Разделить определения контента и состояние игроков. Неизменяемые опубликованные версии; stable IDs; версии схем и capabilities.
Экономика: ledger с reason, source_id, idempotency key, лимиты целых значений и запрет отрицательных остатков. Обновление и получение награды одной транзакцией.
Рейтинги: блокировки/версионные записи и завершение сезонов отдельным контролируемым процессом.
Авторизация гостя: серверный случайный секрет с защищенным хранением на Android, не один device_id. Привязка не создает второй прогресс.
Пароли/коды: проверенные password-hash функции, rate limits и отзыв сессий; не самописная криптография.

## Безопасная публикация
Импорт в карантин → проверка структуры/ссылок/версий → diff → разрешение конфликтов → общий черновик → preview → ручное publish.
Prepare: создать неизменяемые файлы, проверить все связи и план изменения состояния. Commit: атомарно переключить указатель версии; длительные миграции через журналируемый resumable job с явным барьером доступности.
Бой сохраняет старый снимок до завершения. Клиент активирует комплект целиком в безопасной точке. Проверки удаления и компенсаций до публикации.
Откат указателя контента не отменяет автоматически покупки и компенсации; нужны обратные либо корректирующие операции ledger.

## Модель жителей
Житель - отдельный account_type с обычной игровой командой. Реальные онлайны считаются отдельно от жителей через heartbeat TTL и очищаются после обрыва.
Детерминированная событийная модель поведения, шаблоны с безопасными переменными, память и отношения. Будущий LLM не получает права прямой выдачи товаров/изменения рейтинга: возвращает предложения действий для проверяемого движка.
