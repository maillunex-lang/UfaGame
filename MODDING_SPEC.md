# ZIP-модификации UfaGame, спецификация ug-content/1
Статус: реализовано в S12–S14 (ADR 0013): строгие схемы, карантинная проверка, импорт с отчетом/конфликтами и экспорт в Studio. Работающий пример: examples/ufa_batyrs_starter. Инструкция для внешнего ИИ: docs/MOD_AUTHORING.md. Это content ZIP, не Godot PCK/проект и не пакет исходного кода.

## Структура
manifest.json - идентификатор пакета/игры/формата, version, base_content_version, required_capabilities, dependencies, files.
operations.json - упорядоченный список create/replace/delete.
entities/ - определения объектов JSON; resources/ - метаданные ресурсов (mod_resource); assets/ - только PNG и PCM WAV; README.md - описание при наличии, тоже в files.
manifest не включается в собственный files, остальные файлы перечисляются ровно один раз. Нет скрытых неперечисленных файлов.
UTF-8; относительные POSIX paths; stable IDs вида domain_name. Исходные названия и игровые строки на русском допустимы; пути предлагаем ASCII для переносимости.
Manifest не является криптографической подписью: sha256 обнаруживает повреждение, доверие дает владелец при ручном импортировании/публикации.

## Manifest
Обязательные поля: format="ug-content/1", package_id, package_version (semver), game_id="ufagame", base_content_version (точная версия), required_capabilities (массив строк), dependencies (массив package_id + version range), files (массив path/size/sha256).
Семантика: пакет применим к указанной базе. Несовпадение не принудительно игнорируется: импорт предлагает rebase/разрешение конфликтов с новой базой и повторную проверку.
required_capabilities - например dialogue.template.v1, ui.layout.v1. Неизвестная capability блокирует импорт с отчетом о необходимой разработке.

## Операции
create: {op, entity_type, id, source}. Требует отсутствия id.
replace: {op, entity_type, id, source, expected_sha256}. expected_sha256 — SHA-256 канонического JSON заменяемого объекта; несовпадение — конфликт с ручным решением.
resource: {op:"create", entity_type:"resource", id, source:"resources/<id>.json"}; байты ресурса неизменяемы.
delete: {op, entity_type, id, expected_sha256, compensation_rule_id?}. Предварительно определенное правило обязательно для использованных экземпляров; ссылки должны быть разрешены планом замены/миграции. Для неиспользованного объекта отсутствие компенсации допускается только по явному preflight.
source - путь из files к полной JSON-записи того же типа/id, не произвольный JSON Patch.
После импорта все операции применяются только к черновику атомарно. Повтор create не дублирует объект и не молча заменяет его. delete не означает SQL CASCADE.
Расходы, награды, реальные игроки/балансы, секреты и доступы не импортируются как определения контента. Изменение правила экономики не является немедленной выдачей ресурсов.

## Проверки и лимиты
Текущий профиль тестового сервера (S13): архив <=8 МиБ, распакованный <=32 МиБ, <=1000 записей, один файл <=8 МиБ, отношение распаковки <=100; потоковые ограничения действуют независимо от заявленных ZIP размеров. Увеличение — отдельным решением с замером памяти VPS.
Запрет абсолютных путей, ../, обратных слешей, drive prefixes, NUL, symlinks, шифрованных/вложенных архивов, дубликатов и коллизий нормализованных путей/Unicode/case, исполняемых скриптов/библиотек/.tscn/.tres с кодом.
Не доверять расширению: разрешенный тип + декодирование/схема + ограничения dimensions/duration. Ресурс декодировать изолированно с лимитами.
Каждый байт сверить size/hash. Схема, типы/диапазоны, stable IDs, ссылки, граф зависимостей, capability, base revision, сумма вероятностей, достижимость наград.
Архив и JSON не могут задавать shell, SQL, JS, GDScript, произвольные URL действий или пути вне хранилища. Правила только из типизированного реестра готовых узлов.
Упаковщик ZIP не добавляет в прод пакет автоматические подписи доверия. Опубликованный клиентский манифест подписывается отдельным доверенным pipeline.

## Пользовательский путь
Загрузка → карантин → отчет → diff → решение конфликтов → транзакция черновика → preview → ручная публикация.
Любая ошибка оставляет текущую опубликованную версию и черновик до импорта неизменными.
Rollback опубликованного контента не отменяет автоматически ledger/компенсации. Для миграций требуются journal, resume, dedupe и корректирующий план.
Перед выдачей другим ИИ экспортировать capabilities, схемы нужных сущностей, текущую base_content_version, примеры и snapshot выбранных объектов. Нельзя просить ИИ угадать неподтвержденный формат.
